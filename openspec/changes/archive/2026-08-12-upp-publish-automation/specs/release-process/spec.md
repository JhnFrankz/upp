# Release Process Specification

## Purpose

Defines how upp releases are published: `make publish` guards and creates the version tag locally, CI builds assets and creates the GitHub Release idempotently on tag push, and the published release MUST satisfy the self-update contract (see Self-Update Specification).

## Requirements

### Requirement: Publish Guards

`make publish` MUST abort with a clear message and non-zero exit, creating nothing, unless ALL guards pass: working tree clean, current branch `main`, `VERSION` parses as clean `vX.Y.Z`, and the tag exists neither locally nor on the remote.

| Scenario | GIVEN | WHEN | THEN |
|----------|-------|------|------|
| Dirty tree | Uncommitted changes present | `make publish` | Abort: "working tree not clean", exit non-zero, no tag |
| Wrong branch | Current branch is not `main` | `make publish` | Abort: "must run on main", exit non-zero |
| Invalid version | `VERSION=1.2.0` or `VERSION=v0.2.0-rc1` | `make publish` | Abort: "version must match vX.Y.Z", exit non-zero |
| Tag exists locally | Tag `v0.2.0` exists | `make publish VERSION=v0.2.0` | Abort: "tag already exists", exit non-zero |
| Tag exists remotely | `v0.2.0` exists on origin only | `make publish VERSION=v0.2.0` | Abort, exit non-zero |
| Happy path | Clean tree, on main, `v0.2.0` absent | `make publish VERSION=v0.2.0` | Annotated tag `v0.2.0` created and pushed to origin |

### Requirement: Tag Semantics

`make publish` MUST create an annotated tag (`git tag -a`) whose name is exactly `vX.Y.Z` with numeric X, Y, Z. Prerelease tags (`-rc`, `-beta`, `-pre`) MUST be rejected. Tags MUST be created only locally by `make publish`; CI MUST NOT create tags.

| Scenario | GIVEN | WHEN | THEN |
|----------|-------|------|------|
| Annotated tag | All guards pass | `make publish` | `git tag -a vX.Y.Z` with message, pushed to origin |
| Prerelease | `VERSION=v0.2.0-rc1` | `make publish` | Rejected by version guard, no tag |
| CI tag creation | CI has no user prompt | Job runs | CI never creates or pushes tags |

### Requirement: CI Release Gate

CI MUST create a GitHub Release only for tag pushes matching `refs/tags/v*`, and only after the `test` and `lint` jobs pass (`needs: [test, lint]`). `workflow_dispatch` runs MUST build and upload artifacts but MUST NOT create a Release.

| Scenario | GIVEN | WHEN | THEN |
|----------|-------|------|------|
| Tag push, CI green | `v0.2.0` pushed; test, lint pass | Release job | Release created from CI-built assets |
| Tag push, CI red | `v0.2.0` pushed; test fails | Release job | Skipped; no release |
| Dispatch | `workflow_dispatch` run | Release job | Assets built and uploaded; NO release created |
| PR push | Push to a PR branch | Release job | No release |

### Requirement: Idempotent Release Creation

The release job MUST use create-or-upload semantics: create the Release if none exists for the tag; otherwise upload only missing assets without recreating or modifying anything. Re-running the job on an existing tag MUST complete successfully. Recovery from a failed run MUST be re-running CI on the same tag; a published tag MUST NOT be retracted.

| Scenario | GIVEN | WHEN | THEN |
|----------|-------|------|------|
| First run | No release for `v0.2.0` | Job runs | Release created with all assets |
| Re-run | Release exists, all assets present | Job re-runs | Completes; nothing recreated or modified |
| Partial upload | Release exists, assets missing | Job re-runs | Missing assets uploaded; existing untouched |
| Failed run recovery | Previous run failed mid-upload | Re-run on same tag | Completes idempotently; tag unchanged, never deleted |

### Requirement: Asset and Checksums Contract

The Release MUST contain exactly the assets `make release` produces: `upp-linux-amd64.tar.gz`, `upp-linux-arm64.tar.gz`, `upp-darwin-amd64.tar.gz`, `upp-darwin-arm64.tar.gz`, `upp-windows-amd64.zip`, and `checksums.txt`. `checksums.txt` MUST be generated by `make release` in sha256sum `"<hex>  <name>"` format with one line per uploaded asset. `make release` MUST remain the sole generator of assets and checksums. A missing checksums.txt or missing entry MUST cause `upp self-update` to fail closed (see Self-Update Specification: Download and Checksum Verification).

| Scenario | GIVEN | WHEN | THEN |
|----------|-------|------|------|
| Complete release | Release job completes | Inspect release | 5 archives + checksums.txt, one sha256 line each |
| Sole generator | Assets are needed | Any other producer | MUST NOT exist — `make release` only |
| Missing checksums | checksums.txt absent from release | `upp self-update` | Refuses update, fail closed (per Self-Update spec) |

### Requirement: Curated Release Notes

Release notes MUST follow the repository convention and MUST NOT be auto-generated: title `upp vX.Y.Z — <summary>` with a human-written summary, a `## What's new` section with bullet points, a `## Assets` section listing the uploaded files, and a warning that checksums.txt MUST keep shipping with every release.

| Scenario | GIVEN | WHEN | THEN |
|----------|-------|------|------|
| Publish | Release created in CI | Notes assembled | Title, What's new, Assets, checksums warning present |
| Curated summary | Maintainer provided a summary | Notes | Human summary used; no auto-generated changelog |

### Requirement: Release Job Permissions

The release job MUST request `contents: write` scoped to that job only. All other jobs and the workflow top level MUST keep `contents: read`. No additional permissions MAY be granted.

| Scenario | GIVEN | WHEN | THEN |
|----------|-------|------|------|
| Release job | Publish step needs write access | Permissions resolved | `contents: write` on release job only |
| Other jobs | test/lint run | Permissions resolved | `contents: read` from top level, unchanged |

### Requirement: Release Documentation

The README Release section MUST document `make publish` as the publishing path: guarded tag creation locally, CI completing the release. Instructions for manually attaching assets to a GitHub Release MUST be removed.

| Scenario | GIVEN | WHEN | THEN |
|----------|-------|------|------|
| New release | Maintainer follows README | Publishing vX.Y.Z | `make publish`, CI creates release; no manual attach steps |
